## What these tools have in common (interpretation)
No tool read keeps a big project legible by shrinking it. Six moves came up again and again:
1. **Group, then fold the group** (Notion, Obsidian Bases, Asana sections, ClickUp groups, Spatial Task Graph, Jira parents).
2. **A rollup instead of the items**: "N of M done" as a bar or percentage per group (Notion rollup, Jira epic bar, Linear milestones, Asana portfolio).
3. **Hide finished work** (Project Manager Enhanced "Hide done in Gantt", Spatial Task Graph, Jira filters).
4. **Filter to one chain or one group** (Project Planner upstream / downstream, saved filters, Linear milestone filter).
5. **Counts in the group header** (GitHub Projects field sums, monday group summary).
6. **Zoom and drill-down** (Notion zoom and load limit, GitHub Month/Quarter/Year, Project Planner day/week/month): the one move a view-only picture cannot copy.

I found **no tool that makes a static, slide-sized picture that simplifies itself as the project grows**. Their answer is interaction (open the group, zoom in, filter). For a picture, the practice that remains is the status-deck one (`plan-map-large-graph-research.md`, pattern 9): one overview page, a few numbers, a short "needs attention" list.

**Implement here:** rollup bar per group = mock-up M3 (needs a group). Sub-items as a property on a card = the "2/4 subtasks" text already on cards (done).

### Jira (Advanced Roadmaps / Plans)
[Atlassian: tracking progress and status](https://confluence.atlassian.com/advancedroadmapsserver/tracking-progress-and-status-814212695.html) (page read): each bar carries progress (grey = none, green = share done); a parent shows an **aggregated bar of its children** and expanding it shows them; progress counts resolved children or estimates; a warning appears when a done parent has open children. ### Asana, monday, ClickUp, Miro (weakest evidence)
- **Asana Timeline:** subtasks open from an arrow, **only the first level of subtasks shown**; dependencies are drawn by dragging a connector; sections can be collapsed ([help: plan and execute projects with timeline](https://help.asana.com/s/article/plan-and-execute-projects-with-timeline), search summary; the direct help page I tried returned 404). Collapse of sections in Timeline: **confirmed** by an Asana community-manager reply (see Verification pass); the official help article could not be read (it needs JavaScript). Portfolios (earlier doc, page read) show status and progress per project.
- **monday.com:** Gantt with dependencies and milestones; a dashboard "battery" widget for progress; "Show Group Summary" option ([support page](https://support.monday.com/hc/en-us/articles/360015643840), search summary; the page itself returned 403). Baselines, critical path and group summary were then read on monday's own help centre: see Verification pass.
- **ClickUp:** Gantt with a **Show critical path** switch (red path) and collapsible groups ([ClickUp help](https://help.clickup.com/hc/en-us/articles/40982447293207-How-to-use-Gantt-charts-for-project-planning), search summary; page returned 403). The official article was read through the help-centre text: see Verification pass.
- **Miro:** frames act as slides (reorder, hide, export); a Dependencies app links cards; Miro's own help text lists a minimap, fit-to-screen and a frames panel (see Verification pass; the first pass found none) ([Miro help: presentation mode](https://help.miro.com/hc/en-us/articles/8512850754962-Interactive-Presentation-Mode), [dependency mapping](https://miro.com/agile/dependency-mapping), search summary). **The nearest thing to "one slide per group" is a frame per group.**

**Lesson:** all three scale with collapse and critical-path filters, both interactive; Miro's frames are the only "deck from one canvas" idea. **Implement here:** critical path is not possible (no durations); frames = earlier P2 (one picture per group).

### Mermaid and diagram-as-code
- **Treemap** (`treemap-beta`): nested rectangles sized by a number; the docs warn very small values are hard to see or label and deep hierarchies are hard to read ([Mermaid docs](https://mermaid.js.org/syntax/treemap.html), page read). Poor fit: 59 equal to-dos have no size, no links.
- **Kanban:** columns and cards with optional `assigned`, `ticket`, `priority`; one config option only ([docs](https://mermaid.js.org/syntax/kanban.html), page read). No status marks beyond priority, no grouping or rollup. A flat board of 59 cards would be as unreadable as today's map.
- **Collapsible subgraphs** (v11.17.0+) and Graphviz clusters: in `plan-map-large-graph-research.md`. Lab Kit already does not use Mermaid for this picture, so these are examples of the idea only.

### Where a group could come from (derived, re-runnable: `my_work/mockups/plan-map-export-src/goals.ts`)
- **The end goal a to-do leads to does not work as a group.** On the 59 to-do project there are 20 end goals, but **36 of the 59 to-dos (20 of the 24 open ones) lead to the single goal "Supervisor review of draft"**, and 8 to-dos are linked to nothing. So a group cannot be computed from `after` links alone.
- Options that exist or are cheap (interpretation, not checked in code): a new property on the to-do; the experiment the to-do links to (`PlanRow.experiment` already holds the lab note's name and Status, `src/planning/plan.ts:30`; corrected 2026-10-20, the first version of this line wrongly said it was not read); who it is waiting on (`waiting`, only set on some); the parent to-do (conflicts with using subtasks for small steps).
- M1 and M4 need none of these: M4's dot columns are the plugin's own steps.

## Ranked recommendation (for the owner to decide; nothing chosen)
1. **M4 one-pager first, as the large-project picture** (and as a block option): no new field, one picture, readable on desktop and phone, answers "where are we and what needs me now". It subsumes earlier P3 (the lists) and adds the whole-project dot wall. Switch to it when option A's smallest text would fall under 22 px.
2. **M3 progress table second**, only if the owner is willing to give to-dos a group (best phone picture; the group also feeds M2 and the earlier P1 / P2).
3. **M1 open-work graph third**, for owners who want the arrows back on a big project; slide only, and it shrinks again once many to-dos are open.
M2 last: it names every open to-do but loses the arrows and needs the group.

### What M1 still needs before it can be planned as a phase of `plan-map-export.md`
A phase would sit after Phase 2 (status marks, header, key) and reuse its status rules. What the engine must do (pure code in `src/planning/`, tested before any drawing):
1. **Open work only.** Draw the open parent to-dos; finished ones are only the header count. Status (late, waiting, can start, waits for an earlier step) is computed from the **whole** plan first, then filtered, so a done blocker never makes something look blocked and a late to-do keeps its mark. Needs `PlanRow.waiting` kept (Phase 1 of the plan).
2. **Layout.** Reuse `layoutPlan` (steps, places) on the open rows; steps run top to bottom, places across. `mapGeometry` has fixed card sizes (`CARD_W` 190 x `CARD_H` 108), so it needs a chip-size parameter (or a second geometry function). Chip text is 22 px, two lines, so chip width follows the number of places: 6 places gave 259 px (about 17 characters a line); **a rule is needed for more than about 6 places or 9 steps** (the prototype has none): fold the furthest steps into one count row ("+N later, k late, w waiting") rather than shrink below 22 px.
3. **Arrows.** The prototype draws plain curves; long arrows cross chips (for example "GPC of diblocks" to "Scale up diblock to 5 g"). The engine's router (`hitsCard`, routed lanes) must work with the new chip size; arrows into a folded row end at its count.
4. **Cap and counts.** Loose to-dos: a row of chips that fit, urgency order (late, waiting, can start, then name), one count chip with late / waiting counts. Same rule for the folded steps. Totals must add up (open = drawn + counted), tested.
5. **Status marks and key.** Border colour (new pair), dashed for "waits for an earlier step", no corner dot if Q6 (a); header and one-line key from Phase 2; "as of" date. 6. **Properties on chips (Q5).** Optional second line (experiment name · Status; maybe due) only on action chips; chip height then varies, so row height is the maximum in the row and the 22 px / row-count budget is re-checked.
7. **Subtasks.** The prototype shows only the count ("0/3"); the earlier owner decision "subtasks as today" (strip under the card) applies to option A. Confirm that M1 shows counts only.
8. **22 px minimum by construction.** Every text is 22 px or more, so `minText` is a constant; a test asserts it (as `slideSvg` already measures through `note()`), and the fold rule is what keeps it true.
